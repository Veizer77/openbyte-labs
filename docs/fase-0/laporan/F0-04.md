# Laporan F0-04: Kelayakan Better Auth tanpa email

- **Tanggal:** 28 Oktober 2026
- **Status usulan:** REVIEW, API versi terkunci mendukung rancangan awal; N-02 belum terbukti.
- **Baseline:** branch `refactor/prd-v1-5-reset`, HEAD `fd1a98703857dbdc137788cc4aaa63140501fd8c`; working tree reset belum di-commit.
- **Paket yang diperiksa:** `better-auth@1.7.14`, `@better-auth/core@1.7.14`, schema/adapter Drizzle yang terpasang.
- **Wilayah tulis:** laporan ini saja. Tidak membuat endpoint/auth flow atau mengubah schema.

## Kesimpulan

Better Auth versi terkunci menyediakan email/password, signup tertutup, adapter Drizzle, plugin TOTP dan backup codes. Flow dapat berjalan tanpa layanan pengiriman email jika account dibuat melalui jalur admin/CLI yang disetujui, email verification tidak diwajibkan, dan callback pengiriman email tidak dipasang. Istilah “tanpa email” di laporan ini berarti **tidak mengirim email**. Route email/password bawaannya tetap memakai identifier berformat email; jika pemilik bermaksud login username tanpa email, itu keputusan produk terpisah dan prototype saat ini justru menampilkan field email.

Paket/API saja tidak menegakkan owner/editor, kewajiban enroll TOTP untuk user yang belum mengaktifkannya, larangan trusted device, lockout password 5/15, keamanan seluruh Server Actions, audit aplikasi, atau recovery CLI. Keputusan tersebut perlu diimplementasikan dan diuji sebelum N-02.

## API yang diverifikasi pada versi terpasang

1. `emailAndPassword` memiliki `enabled`, `disableSignUp` (default false) dan `requireEmailVerification`. Route `signInEmail` menerima `email` dan `password`. Rancangan yang sesuai PRD adalah password sign-in dengan signup publik ditutup, tanpa provider pengiriman email dan tanpa email reset; password/recovery ditangani oleh CLI/service terkontrol.
2. `better-auth/plugins` mengekspor `twoFactor`. Plugin menyediakan TOTP URI, enable/verify, recovery/backup code, serta penambahan model two-factor ke schema. Default `skipVerificationOnEnable` adalah false, sehingga enrollment semestinya menunggu verifikasi kode sebelum faktor aktif.
3. Implementasi versi ini mengenkripsi TOTP secret memakai `symmetricEncrypt`. Default `backupCodeOptions.storeBackupCodes` bernilai `encrypted`. Hasil backup codes hanya ditampilkan ketika dibuat; `auth.api.viewBackupCodes` adalah API server-only untuk melihat versi terdekripsi dan bukan endpoint HTTP klien. Key `BETTER_AUTH_SECRET` karenanya wajib dijaga, dirotasi melalui rencana, dan tidak dicatat.
4. Pada sign-in email untuk user dengan 2FA aktif, plugin menghapus session awal dan cookie session, menghapus record session sementara, lalu membuat cookie challenge bertanda tangan `two_factor`. Setelah verifikasi berhasil barulah plugin membuat session penuh. Jadi status yang akurat selama challenge adalah **pending 2FA / belum terautentikasi**, bukan session berhak terbatas. Request ke admin saat challenge harus gagal.
5. Plugin menerima `trustDevice` pada verifikasi TOTP dan default `trustDeviceMaxAge` adalah 30 hari. `TwoFactorOptions` yang diperiksa tidak memperlihatkan boolean `disableTrustDevice`. Karena PRD meminta TOTP wajib, jangan tampilkan/terima trusted device sampai cara menutup jalur langsung ini dibuktikan. Menghilangkan tombol saja bukan kontrol yang cukup.
6. Plugin menyediakan `accountLockout.maxFailedAttempts` dan `durationSeconds`; default-nya 10 dan 900 detik. Konfigurasi dapat menyatakan 5/900 untuk kegagalan verifikasi faktor kedua. Endpoint `/two-factor/*` juga mempunyai rate limit 3 panggilan/10 detik. Lockout ini hanya mencakup verifikasi 2FA, bukan kegagalan password/email sign-in. Kebutuhan PRD 5 upaya login gagal dalam 15 menit tetap memerlukan kebijakan aplikasi yang diuji, termasuk percobaan paralel dan interaksi dengan counter TOTP.

## Kontrak auth yang diusulkan untuk koordinator

- Aktor tanpa sesi valid adalah `anonymous`; cookie challenge 2FA tetap dianggap unauthenticated; session penuh baru menjadi `authenticated_owner` atau `authenticated_editor` sesudah policy memuat profil domain terpercaya.
- Simpan `role` hanya pada profil domain (`users`), terikat unik ke Better Auth user. Jangan menerima role dari form/browser atau menggunakan role dari client.
- Tolak route/action admin jika tidak ada session penuh, faktor TOTP belum enabled-and-verified, profil domain tidak ada, sesi dicabut/kedaluwarsa, atau policy resource/operation/field menolak.
- Signup publik tertutup. Enrollment TOTP diperlukan sebelum user baru dapat memakai admin. Recovery/reset lewat owner CLI terkontrol, tanpa email, dengan konfirmasi, audit tanpa secret dan pencabutan session lama.
- Batasi endpoint Better Auth yang benar-benar diperlukan. Uji `/sign-up/email`, password reset, sign-in, TOTP, backup code, logout/revoke dan semua alias route; jangan mengandalkan UI.
- Periksa batas sesi, cookie `httpOnly`, `secure` produksi, `sameSite`, origin/CSRF, lockout dan trust-device pada request langsung.

## Ketidakselarasan kontrak dan tindak lanjut rekonsiliasi

Pada saat audit, `docs/fase-0/kontrak.md` versi 1.0.0 menyatukan keadaan password-only dan 2FA pending di bawah satu istilah seolah sesi masih aktif. Bukti plugin membedakan dua keadaan: sesi dapat ada bagi akun yang belum mengaktifkan TOTP, sedangkan challenge TOTP akun yang faktornya aktif tidak mempertahankan sesi awal. Draft rekonsiliasi versi 1.0.1 kini memisahkan `password_only` (sesi akun belum enroll, hanya enrollment terbatas) dari konteks `pending_2fa` (challenge unauthenticated); keduanya tidak mendapat akses admin. Draft juga menandai duplikasi `name`/`email` auth-domain sebagai blocking dan memerlukan keputusan sumber identitas/sinkronisasi sebelum schema/migration final.

Kontrak hasil rekonsiliasi tetap belum disetujui. Lockout 5/15 dicatat sebagai target kebijakan aplikasi; API plugin yang diperiksa hanya mencakup lockout second-factor, bukan bukti lockout password atau seluruh kombinasi percobaan. Trust-device ditandai tidak boleh aktif sebelum bypass request langsung ditutup dan diverifikasi. Tidak ada implementasi atau pengujian runtime baru.

## Verifikasi dan batas

- Dibaca dari paket terpasang: `package.json`, type definitions email/password, TOTP, plugin two-factor, implementasi challenge/lockout dan backup-code encryption.
- Tidak dikirim email, tidak dibuat user, tidak dibuka endpoint, tidak diakses database dan tidak dilakukan browser/request E2E.
- Tidak diverifikasi: clean build auth dengan adapter/schema final, cookie/origin pada Next runtime, race lockout, enrollment owner/editor, recovery CLI, session revocation, serta tidak adanya bypass pada route/action.

## Handoff

Tindak lanjut: review draft kontrak `docs/fase-0/kontrak.md` §4 dan §7; putuskan field identitas otoritatif serta detail counter lockout dan recovery. Arti “tanpa email” dibatasi ke tidak mengirim email, sementara identifier Better Auth tetap berformat email; bila yang dimaksud username, perlu keputusan produk. Setelah keputusan dan bukti API/runtime tersedia, auth dapat diimplementasikan dan diuji lewat jalur langsung. N-02 tetap terbuka.
