## Pemeriksaan lokal target DB

`scripts/db-migrate.mjs` memilih `DATABASE_URI_DIRECT || DATABASE_URI`, memanggil guard lalu membuka koneksi Postgres dan menjalankan migrasi. `scripts/db-guard.mjs` menolak host non-local secara default, tetapi `ALLOW_DB_MIGRATE=true` mengizinkan host remote apa pun; flag ini tidak mengikat host, nama database, branch Neon, atau environment yang telah disetujui. Karena itu flag tersebut bukan allowlist target tes yang aman.

`scripts/db-check.mjs` memeriksa keberadaan SQL migration dan menguji satu URI remote sintetis ditolak ketika flag tidak ada. Script tidak membuka DB, memeriksa drift/schema, menjalankan migrasi, atau membuktikan bahwa target remote yang diizinkan adalah disposable. `drizzle.config.ts` memakai URI direct dengan fallback ke URI runtime dan tidak memanggil safety guard.

Migrasi yang ditemukan saat audit bernama `src/db/migrations/0000_magenta_iron_patriot.sql`. Laporan F0-08 yang sudah ada menyebut `0000_luxuriant_drax.sql`; nama itu tidak terdapat di direktori saat pemeriksaan. Perbedaan ini dicatat untuk reviewer, bukan diperbaiki oleh F0-05.

### Uji sintetis yang benar-benar dijalankan

Perintah inline Node mengimpor hanya `assertSafeDatabaseTarget` dan memakai URI contoh `remote.example.invalid`; tidak membuat koneksi. Hasil: **PASS** untuk URI hilang ditolak, URI malformed ditolak, localhost diterima, remote tanpa flag ditolak, dan remote sintetis dengan `ALLOW_DB_MIGRATE=true` diterima. Hasil terakhir mengonfirmasi batas guard: flag membolehkan target remote apa pun. Tidak ada database yang disentuh.

## Rancangan isolasi sebelum tes berizin

1. **Vitest:** fungsi murni memakai fixture sintetis; test DB tidak membaca `.env` pemilik dan menerima target khusus `test`. Jika membutuhkan DB, job menyalakan PostgreSQL versi yang disetujui dalam service/container per-job, database/volume unik dan dihancurkan hanya oleh job itu.
2. **Migrasi Neon:** hanya branch/database tes yang dipisah dari `main` production dan `dev` staging, data sintetis, koneksi direct tes, kredensial least-privilege dan identitas host+database yang eksplisit di allowlist. Target tidak cocok berarti abort sebelum connect. Mutasi/penghapusan perlu persetujuan terpisah.
3. **R2:** bucket tes independen dengan credential scope bucket/prefix minimum. Pisahkan media publik, private dan backup. Key object dibuat server/test-run, cleanup hanya pada key test-run yang tercatat dan setelah pemilik memberi izin.
4. **Sentry:** project/environment tes terpisah dan payload sintetis; sanitasi secret, cookie, email, IP dan data pelanggan sebelum kirim.
5. **CI:** gunakan PostgreSQL service disposable bila integrasi DB diperlukan; pisahkan env/credential setiap job; jangan memberikan secret production pada pull-request dari fork.
6. **Backup/restore:** hanya dump database tes sintetis, passphrase melalui secret channel, bucket backup tes, restore ke DB baru yang kosong dan dicek targetnya. Jangan menimpa DB existing.
7. **Pembersihan:** tulis manifest target yang dibuat test (nama DB/branch, bucket key/prefix, TTL); hapus hanya target exact yang diverifikasi. Tidak ada cleanup wildcard atau deletion tanpa izin.

Sebelum remote migration, guard perlu diperkuat oleh pemilik file dengan fail-closed allowlist identitas target (host/database/environment), bukan hanya boolean `ALLOW_DB_MIGRATE`. Kriteria ini dicatat pada draft rekonsiliasi `docs/fase-0/kontrak.md` §5 dan §7. F0-05 tidak mengubah script, menguji ulang source, atau menyetujui target; temuan sintetis tetap blocker sampai guard diperbaiki dan diuji sebelum koneksi.
