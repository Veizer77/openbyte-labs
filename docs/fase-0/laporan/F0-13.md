## Perilaku yang diverifikasi

1. **Deteksi format dari byte.** PNG (`89 50 4E 47`), JPEG (`FF D8 FF`), WebP (`RIFF…WEBP`), GIF, AVIF (`ftyp`+brand), SVG (teks `<?xml`/`<svg` termasuk BOM) dikenali; selain itu `unknown`.
2. **Urutan validasi.** Ukuran byte → magic number → decode `sharp`. Berkas 2 KB dengan batas 1 KB ditolak `TOO_LARGE` tanpa decode.
3. **SVG ditolak mutlak** (`SVG_REJECTED`, HTTP 415), termasuk yang memuat `<script>` dan yang diawali BOM.
4. **GIF, teks, dan format di luar whitelist** ditolak `UNSUPPORTED_TYPE` (415).
5. **Berkas rusak** (PNG terpotong 40 byte, `ftypavif` tanpa payload gambar) ditolak `DECODE_FAILED` (422) — header tidak dipercaya.
6. **Dimensi** di bawah 320×200 atau di atas 8000×8000 ditolak sebelum resize.
7. **Empat varian WebP** dihasilkan dari satu sumber 1200×800: `thumb` 320×320 (cover), `card` 960×640, `hero` 1200×800, `og` 1200×630. Sumber 400×300 tidak diperbesar (`hero` ≤ 400×300).
8. **Determinisme:** dua pemrosesan input identik menghasilkan byte identik.
9. **Object key** `media/2026/10/{id}/{variant}.webp` memakai tanggal UTC; ID wajib cocok `^[A-Za-z0-9_-]{21,32}$`.
10. **Nama berkas klien** `../../etc/passwd`, `a/b.jpg`, `.env`, karakter kontrol, dan nama > 200 karakter ditolak; nama sah dikembalikan sebagai metadata tanpa memengaruhi tipe.
11. **Ekstensi tidak menentukan tipe:** byte PNG bernama `sebenarnya-png.jpg` tetap tervalidasi sebagai `png`.

## Penyimpangan kontrak dan keputusan yang diperlukan

1. **Nama varian bertentangan.** `docs/fase-0/kontrak.md` §5 menulis `thumb/sm/md/lg` (150/640/1280/1920), sedangkan PRD §2.1 dan §3.8 menulis `thumb/card/hero/og`. Implementasi mengikuti **PRD**; kontrak perlu direvisi agar tidak ada dua kebenaran.
2. **Dimensi varian belum diputuskan pemilik.** Nilai saat ini (320×320, 960w, 1920w, 1200×630) adalah nilai teknis awal di `MEDIA_VARIANT_SPECS`, satu titik ubah. Butuh konfirmasi.
3. **Batas ukuran 8 MB** dipilih karena PRD §6.2 mewajibkan "batas ukuran" tanpa angka untuk media admin (angka 5 MB di PRD hanya untuk lampiran klien Rilis 2). Butuh konfirmasi pemilik.
4. **AVIF diterima, GIF ditolak.** PRD tidak menyebut AVIF; `sharp` mendukungnya. Bila pemilik ingin whitelist lebih sempit, ubah `allowedFormats`.
5. **Mapping `heif` → `avif`** diperlukan karena `sharp` melaporkan AVIF sebagai `heif` pada sebagian versi; tanpa mapping, AVIF sah akan gagal `TYPE_MISMATCH`.
